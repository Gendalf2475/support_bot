# Омниканальный support-бот

Бот принимает обращения из Telegram, Discord и VK, проводит пользователей через настраиваемую форму тикета и отправляет оформленный тикет в topic/forum thread Telegram-группы поддержки. Telegram остаётся единым рабочим местом администрации: сотрудники отвечают только из topic, а бот отправляет ответ обратно в платформу пользователя.

## Что нужно заранее

- Python 3.11 или новее.
- Telegram-группа поддержки с включёнными Topics/Forum.
- Токен бота от BotFather.

## Миграции и запуск

```bash
alembic upgrade head
python -m app.bot.main
```

Через Docker:

```bash
docker compose up -d --build
```

В `docker-compose.yml` для сервиса задано `restart: unless-stopped`.

Миграции создают `users`, `message_maps`, `tickets`, `ticket_answers`, `ticket_answer_media` и добавляют поля для причин закрытия, напоминаний, автозакрытия, предупреждений, ожидания ответа пользователя, пропущенных ответов, служебных сообщений тикета, порядка медиа, `media_group_id`, омниканальных платформ, сохранённого `minecraft_nickname`, времени его последней смены и результата проверки игроков через Minecraft API. Старые Telegram-пользователи получают `platform=telegram`, а `platform_user_id` заполняется старым `telegram_id`.

## Как работает тикет

Пользователь отправляет `/start` в ЛС. Бот сразу показывает reply-клавиатуру с доступными формами из `config/ticket_forms.yml`.

Пользователь выбирает форму, отвечает на вопросы по очереди, проверяет итог и нажимает `Отправить`.

После отправки бот создаёт или использует существующий topic пользователя в группе поддержки, отправляет туда карточку `🟣 Новый тикет #...`, пытается закрепить карточку и отправляет все медиа ниже карточки. Если в одном вопросе несколько фото/видео, бот старается отправить их одним альбомом через `sendMediaGroup`; несовместимые типы файлов или неудачная отправка альбома обрабатываются fallback-отправкой по одному файлу. Порядок файлов сохраняется.

Ниже тикета бот отправляет служебное сообщение `Управление тикетом #...` с reply-клавиатурой поддержки `✅ Закрыть тикет`. Inline-кнопка закрытия для новых тикетов больше не используется.

Пока тикет активен, любые новые сообщения пользователя в ЛС копируются в этот topic. Ответы поддержки из topic копируются пользователю в ЛС. Когда администратор отвечает из topic, тикет переходит в `waiting_user` и сохраняет `last_support_message_at`. Когда пользователь отвечает, тикет возвращается в `in_progress`, обновляет `last_user_message_at` и сбрасывает отложенные пользовательские предупреждения. Если пользователь пишет `/start` при активном тикете, бот сообщает, что тикет уже открыт.

При каждом новом сообщении или нажатии кнопки в ЛС бот обновляет `username`, имя пользователя и `updated_at` по данным Telegram. Если пользователь сменил username или имя, новый тикет и `/status` будут показывать актуальные данные, а существующий topic будет автоматически переименован при следующем обращении, если у бота есть право редактировать forum topics.

После закрытия тикета пользователь сразу получает reply-клавиатуру с формами и может открыть новый тикет без повторного `/start`. Topic при этом переиспользуется: один пользователь = один topic.

Активными считаются только статусы `open`, `in_progress`, `waiting_user`. Закрытые `closed` и отменённые `cancelled` тикеты игнорируются при `/start`, выборе формы и пересылке пользовательских сообщений, поэтому пользователь может открыть новое обращение сразу после закрытия старого. Закрытие тикета идемпотентно: повторное нажатие старой кнопки причины отвечает `Тикет уже закрыт.` и не меняет `close_reason`, `closed_at` и администратора закрытия.

## Платформы

Telegram-пользователи работают как раньше: `/start`, reply-клавиатуры, inline-кнопки формы, медиа и ответы поддержки через Telegram Bot API.

Discord включается переменной `DISCORD_ENABLED=true` и токеном `DISCORD_BOT_TOKEN`. Используется `discord.py 2.x`; боту нужны DM и Message Content Intent. Discord принимает DM: пользователь пишет боту, выбирает форму через select menu, отвечает на вопросы текстом и attachment-файлами, а действия формы выполняет кнопками. Ответы администрации из Telegram topic уходят пользователю в Discord DM.

Активность Discord-бота настраивается через `.env`: `DISCORD_ACTIVITY_ENABLED`, `DISCORD_ACTIVITY_TYPE` и `DISCORD_ACTIVITY_NAME`. Поддерживаются типы `playing`, `watching`, `listening`, `competing`; неизвестный тип заменяется на `playing` с warning в лог. Presence Intent для этого не нужен. Отдельный логотип активности поставить нельзя: Discord использует аватарку бота из Developer Portal.

VK включается переменными `VK_ENABLED=true`, `VK_GROUP_TOKEN`, `VK_GROUP_ID`. Используется VK Bot Long Poll через `vk_api`; пользователь пишет в сообщения сообщества, выбирает форму keyboard-кнопкой и отвечает текстом/вложениями. Ответы администрации из Telegram topic уходят в VK.

Пользователи разных платформ не смешиваются: ключ пользователя — `platform + platform_user_id`. Telegram user `123`, Discord user `123` и VK user `123` считаются разными пользователями и получают разные topic. Названия topic содержат префикс платформы: `TG | @username`, `DS | username`, `VK | Имя | ID 123`.

Карточка тикета показывает платформу, username, platform ID и имя пользователя. `/status`, `/block`, `/unblock` работают по topic и применяются именно к пользователю этой платформы.

## Автозаполнение Minecraft-ника

Если `MINECRAFT_NICKNAME_REQUIRED_ENABLED=true`, бот добавляет общий вопрос ника перед любой формой из верхнего блока `global_questions` в `config/ticket_forms.yml`:

```yaml
global_questions:
  - id: "minecraft_nickname"
    text: "Введите ваш игровой ник:"
    help_text: "Укажите ник точно так же, как он отображается на сервере."
    required: true
    answer_type: "text"
    profile_field: "minecraft_nickname"
    validation_regex: "^[A-Za-z0-9_]{3,16}$"
    validation_error: "Введите корректный Minecraft-ник: 3–16 символов, латиница, цифры или _."
    locked: true
```

`global_questions` идут перед вопросами выбранной формы. Если старая форма всё ещё содержит свой вопрос с `profile_field: "minecraft_nickname"`, при включённом глобальном нике бот использует глобальный вопрос и пропускает дубликат с warning в лог. Если `global_questions` нет или `MINECRAFT_NICKNAME_REQUIRED_ENABLED=false`, старые формы работают по прежней структуре.

Вопрос можно пометить как профильное поле:

```yaml
questions:
  - id: "your_nickname"
    text: "Введите ваш игровой ник:"
    required: true
    answer_type: "text"
    profile_field: "minecraft_nickname"
    validation_regex: "^[A-Za-z0-9_]{3,16}$"
    validation_error: "Введите корректный Minecraft-ник: 3–16 символов, латиница, цифры или _."
```

Если `profile_field` не указан, бот всё равно считает Minecraft-ником пользователя вопросы с `id`: `nickname`, `your_nickname`, `minecraft_nickname`, `player_nickname`. Введённый ник сохраняется в `users.minecraft_nickname` отдельно для каждого пользователя и платформы: Telegram, Discord и VK не смешиваются. Для ника другого игрока используйте `profile_field: "minecraft_target_nickname"`; fallback по `id` работает для `violator_nickname` и `target_nickname`, но такие значения не сохраняются в профиль пользователя.

При `MINECRAFT_NICKNAME_AUTOFILL_ENABLED=true` бот перед повторным вопросом предлагает использовать прошлый ник кнопками `Да` и `Ввести другой`. Telegram использует inline-кнопки, Discord — buttons, VK — keyboard; текстовый fallback принимает `да`, `ввести другой`, `другой`. Если настройка выключена, бот задаёт вопрос как обычный, но продолжает валидировать и сохранять новый ник для `/status` и будущего включения функции. После изменения `.env` нужен перезапуск контейнера.

Новые настройки профиля ника имеют приоритет над legacy-autofill:

- `MINECRAFT_NICKNAME_LOCK_ENABLED=true` — сохранённый ник считается закреплённым; перед сменой пользователь подтверждает действие кнопкой `Да, изменить`.
- `MINECRAFT_NICKNAME_CONFIRM_EACH_TICKET=true` — перед каждым тикетом бот спрашивает `Ваш игровой ник: Nick?` с кнопками `Да` и `Изменить ник`.
- `MINECRAFT_NICKNAME_CONFIRM_EACH_TICKET=false` — сохранённый ник подставляется автоматически.
- `MINECRAFT_NICKNAME_CHANGE_COOLDOWN_HOURS` — минимальный интервал между сменами ника; `0` отключает cooldown.

В БД ник хранится в `users.minecraft_nickname`, время последней смены — в `users.minecraft_nickname_updated_at`. Ник закрепляется отдельно для каждой платформы: Telegram, Discord и VK профили не смешиваются.

Для `minecraft_nickname` по умолчанию используется regex `^[A-Za-z0-9_]{3,16}$`. Его можно переопределить в YAML через `validation_regex`, а текст ошибки — через `validation_error`.

## Интеграция с MajureSupportAPI

MajureSupportAPI — отдельный Paper/Purpur-плагин Minecraft-сервера. Support bot не использует RCON: он обращается к HTTP API плагина `GET /player/{nickname}` с заголовком `Authorization: Bearer <token>`.

Пример `.env`:

```env
MINECRAFT_API_ENABLED=true
MINECRAFT_API_TYPE=http
MINECRAFT_HTTP_API_BASE_URL=http://127.0.0.1:8085
MINECRAFT_HTTP_API_TOKEN=secret
MINECRAFT_HTTP_API_TIMEOUT=5
MINECRAFT_NICKNAME_CHECK_ENABLED=true
MINECRAFT_NICKNAME_CHECK_STRICT=false
```

`MINECRAFT_API_ENABLED` включает HTTP-интеграцию, а `MINECRAFT_NICKNAME_CHECK_ENABLED` включает проверку при заполнении формы. Если проверка выключена, форма работает как раньше, но карточка тикета покажет `Проверка: отключена` для помеченных Minecraft-полей.

При `MINECRAFT_NICKNAME_CHECK_STRICT=true` пользователь не сможет продолжить с ником, которого API не нашёл, и при недоступном API бот попросит повторить ввод позже. При `false` бот покажет предупреждение и кнопки `Продолжить` / `Ввести другой`; если API недоступен, ник принимается, а предупреждение сохраняется в карточке тикета.

В карточке тикета появляется отдельный блок `🎮 Игровой ник` / `🎮 Проверка игроков` с ником пользователя, статусом проверки, UUID, online-статусом, источником и ошибкой, если API не ответил. Для формы жалобы используйте `minecraft_target_nickname` для нарушителя: он проверяется через API, но не сохраняется как ник пользователя и выводится отдельно как целевой игрок.

Команда `/lookup <nickname>` работает в General и topic группы поддержки. Она вызывает MajureSupportAPI независимо от `MINECRAFT_NICKNAME_CHECK_ENABLED` и показывает результат проверки администратору. Если API выключен или недоступен, бот отвечает короткой ошибкой; токен API не выводится и не логируется.

Если MajureSupportAPI недоступен, support bot продолжает работать. Ошибки HTTP, timeout, connection error и invalid JSON логируются без `Authorization` header.

## Медиа между платформами

Telegram-медиа хранится как Telegram `file_id` и копируется в support topic как раньше.

Discord/VK attachments сохраняются как URL. В Telegram topic бот пытается отправить вложение по URL; если Telegram не принимает файл, отправляет ссылку fallback-сообщением. Если администрация отправляет медиа из Telegram topic пользователю Discord/VK, MVP отправляет fallback-текст, что медиа не удалось переслать в эту платформу. Текстовые ответы обязательны для всех платформ.

После закрытия Telegram-пользователь получает клавиатуру форм, Discord-пользователь получает embed с select menu, а VK-пользователь получает сообщение с keyboard-кнопками форм.

## UX Discord и VK

Discord UI вынесен в `app/bot/channels/discord_ui.py`. Главное меню отправляется embed-сообщением `MAJURE SUPPORT` с select menu, где варианты берутся из `config/ticket_forms.yml`: `id`, `title`, `description`, `button_text`. Если в `button_text` есть ведущий эмодзи, бот использует его как emoji option. Вопросы формы отправляются embed-сообщениями с кнопками `Пропустить` и `Отмена`, несколько медиа подтверждаются кнопками `Продолжить` и `Отмена`, preview тикета показывает кнопки `Отправить`, `Заполнить заново`, `Отмена`.

Discord components имеют ограничение select menu до 25 options. Если форм больше 25, бот показывает первые 25 и пишет warning в лог. Если component устарел или состояние уже изменилось, бот отвечает `Это действие уже неактуально.` и не меняет тикет.

VK UI вынесен в `app/bot/channels/vk_ui.py`. Главное меню отправляется сообщением с keyboard-кнопками форм из `config/ticket_forms.yml`; отключённые формы не попадают в список. Для MVP показывается до 10 кнопок форм, лишние формы логируются warning. Вопросы, продолжение после медиа, preview и меню после закрытия тикета используют VK keyboard JSON с цветами: `primary` для форм, `secondary` для нейтральных действий, `negative` для отмены, `positive` для отправки и продолжения.

Текстовый fallback для Discord и VK сохранён: форму можно выбрать номером, названием, `button_text` или `id`; действия принимают `отправить`, `заново`, `отмена`, `продолжить`, `пропустить`. Это нужно для устаревших кнопок, недоступных components/keyboards и ручного ввода пользователя.

Если Discord, VK или Telegram polling падает, supervisor логирует traceback, оставляет остальные каналы работать и перезапускает только упавший канал с backoff из `CHANNEL_RESTART_DELAY_SECONDS` до `CHANNEL_RESTART_MAX_DELAY_SECONDS`. `CHANNEL_RESTART_MAX_ATTEMPTS=0` означает бесконечные попытки; если задан лимит и он исчерпан, бот завершает процесс с кодом `1`, чтобы Docker restart policy поднял контейнер заново. VK Long Poll timeout считается временной сетевой ошибкой: бот пишет warning `VK Long Poll timeout, reconnecting...`, пересоздаёт Long Poll и уведомляет General только после `VK_TIMEOUT_NOTIFY_AFTER_FAILURES` подряд идущих сетевых ошибок. Повторные уведомления ограничены `CHANNEL_FAILURE_NOTIFY_COOLDOWN_MINUTES`; восстановление отправляется только если до этого было уведомление о падении.

## Формы тикетов

Формы настраиваются в `config/ticket_forms.yml`. Если файл отсутствует или содержит ошибку YAML, бот не падает и использует встроенную fallback-форму `Другое`; ошибка пишется в лог.

Верхний блок `global_questions` задаёт вопросы, которые автоматически добавляются перед вопросами каждой формы. Сейчас он используется для закреплённого `minecraft_nickname`; старый формат без `global_questions` продолжает работать.

Пример вопроса:

```yaml
questions:
  - id: "proof"
    text: "Прикрепите доказательства:"
    help_text: "Можно отправить до 5 файлов: фото, видео или документы."
    required: true
    answer_type: "media"
    allow_multiple: true
    max_files: 5
```

Поля формы:

- `id` — уникальный технический ID формы.
- `title` — название формы для пользователя.
- `description` — описание формы.
- `button_text` — текст кнопки в пользовательской reply-клавиатуре.
- `admin_title` — заголовок тикета для поддержки.
- `success_text` — необязательный текст пользователю после успешной отправки формы. Поддерживает `{ticket_id}`, `{form_title}`, `{platform}`.
- `close_reasons` — необязательный список причин закрытия для этой формы; если списка нет, используются общие причины.
- `enabled` — необязательный флаг; если `false`, форма не показывается в пользовательской клавиатуре.
- `questions` — список вопросов.

Поля `global_questions` такие же, как у обычных вопросов. Если глобальный вопрос `minecraft_nickname` включён, дубликаты этого же профильного поля внутри конкретных форм пропускаются с warning в лог.

Поля `close_reasons`:

- `id` — технический ID причины, сохраняется в `ticket.close_reason`.
- `title` — название причины для topic и карточки тикета.
- `button_text` — текст кнопки для администрации.
- `user_message` — сообщение пользователю после закрытия этой причиной.
- `show_to_user` — если `false`, пользователь получает стандартный текст с названием причины.

Поля вопроса:

- `id` — уникальный технический ID вопроса внутри формы.
- `text` — основной текст вопроса.
- `help_text` — необязательная подсказка, показывается под вопросом как `Подсказка: ...`.
- `required` — `true`, если вопрос обязательный; `false`, если его можно пропустить.
- `answer_type` — ожидаемый тип ответа: `text`, `media` или `any`.
- `allow_multiple` — `true`, если в вопрос можно приложить несколько медиафайлов подряд.
- `max_files` — необязательное максимальное количество файлов для `allow_multiple: true`; если не указано, бот показывает счётчик без лимита (`Файлы добавлены: 3.`).
- `profile_field` — необязательный профильный ключ; сейчас поддерживаются `minecraft_nickname` и `minecraft_target_nickname`.
- `validation_regex` — необязательная regex-валидация текстового ответа.
- `validation_error` — сообщение при ошибке `validation_regex`.

`answer_type: text` принимает текст или caption у медиа. Если пользователь отправит медиа без текста/caption, бот попросит отправить текст.

`answer_type: media` принимает `photo`, `video`, `document`, `voice`, `audio`, `animation`, `sticker`. Если пользователь отправит только текст, бот попросит прикрепить файл, фото, видео или другое медиа.

`answer_type: any` принимает текст или поддерживаемое медиа. Если `answer_type` не указан, используется `any`.

Если у вопроса `answer_type: media` или `answer_type: any` и `allow_multiple: true`, бот не переходит к следующему вопросу после первого файла. Каждый следующий медиафайл добавляется к текущему ответу, а бот показывает общее количество добавленных файлов:

```text
Файлы добавлены: 3 из 5.
Можно отправить ещё файл или нажать «Продолжить».
```

Если пользователь отправляет несколько файлов одним альбомом/media group, Telegram присылает несколько update с одинаковым `media_group_id`. Бот собирает такую пачку в короткий буфер и отвечает только один раз на весь альбом. Если пользователь позже добавляет ещё один файл или новый альбом, бот отправляет новое подтверждение с обновлённым счётчиком.

После первого медиа текущий draft остаётся активным в состоянии сбора медиа. Кнопка `Продолжить` актуальна, пока выбранная форма, текущий вопрос и индекс вопроса совпадают с draft, а вопрос поддерживает `allow_multiple: true`. Если кнопка действительно устарела, бот отвечает `Это действие уже неактуально.` и не очищает форму.

Следующие медиа в этом состоянии не создают новый тикет и не отправляются в поддержку до подтверждения тикета. В preview и карточке тикета отображается количество файлов, например `📎 Медиафайлов: 3`.

Если достигнут `max_files`, лишние файлы не сохраняются, а бот пишет:

```text
Файлы добавлены: 5 из 5.
Достигнут лимит файлов.

Нажмите «Продолжить», чтобы перейти дальше.
```

Для поддержки фото и видео одного вопроса отправляются компактным альбомом/media group, если это принимает Telegram Bot API. Caption можно поставить только на первый элемент альбома, поэтому подписи нескольких файлов бот дополнительно отправляет отдельным текстовым сообщением. Документы, voice/audio, animation, sticker и другие несовместимые типы уходят отдельными сообщениями.

Если `required: false`, под вопросом появляется inline-кнопка `Пропустить`. При пропуске бот сохраняет ответ с `skipped=true` и переходит к следующему вопросу.

Минимальная ручная проверка media-flow после обновления: дойти до необязательного media-вопроса, отправить один файл, нажать `Продолжить`, увидеть preview с `📎 Медиафайлов: 1`; для обязательного media-вопроса нажать `Продолжить` без файла и получить просьбу прикрепить хотя бы один файл; старую кнопку `Продолжить` после перехода к preview нажать повторно и убедиться, что она отвечает `Это действие уже неактуально.` без сброса формы.

Актуальные формы по умолчанию: `Забыл пароль`, `Жалоба на игрока`, `Другое`. Форма `Проблема с донатом` удалена из `config/ticket_forms.yml`; старые тикеты с `form_id=donation_problem` в базе не ломают работу бота. Общий ник пользователя вынесен в `global_questions`, а в форме жалобы отдельно остаётся `minecraft_target_nickname` для нарушителя.

## Команды поддержки

Команды работают только в `SUPPORT_CHAT_ID`. Команды управления тикетом выполняются внутри topic пользователя; `/lookup` можно использовать и в General.

`/block`

Блокирует пользователя. Он не сможет открыть тикет, а его сообщения не будут пересылаться в поддержку.

`/unblock`

Разблокирует пользователя.

`/status`

Показывает платформу, `platform_user_id`, username, имя, Minecraft-ник, `blocked`, `topic_id`, ID открытого тикета, статус тикета и дату создания тикета.

`/lookup <nickname>`

Проверяет игрока через MajureSupportAPI и отвечает в группе поддержки. Команда не пересылается пользователю и не показывает API-токен.

`/debug_user <platform> <platform_user_id>`

Показывает диагностическую карточку пользователя: `user.id`, платформу, platform ID, username, имя, topic ID, `blocked`, Minecraft-ник и последние 10 тикетов со статусами, формой, причиной закрытия и датами. Работает в General и topic, пользователю не пересылается.

`/force_close_user <platform> <platform_user_id>`

Аварийно закрывает все активные тикеты пользователя со статусами `open`, `in_progress`, `waiting_user`. Ставит `close_reason=force_closed_by_admin`, заполняет `closed_at` и `closed_by_telegram_id`, очищает состояние заполнения формы и отвечает количеством закрытых тикетов. Используйте, если состояние пользователя нужно вручную восстановить.

`/debug_state <platform> <platform_user_id>`

Показывает текущее состояние заполнения формы: FSM/draft state, `selected_form_id`, текущий вопрос, количество ответов, количество медиа, pending action и активный тикет. Для Telegram читает aiogram FSM, для Discord/VK — внутренний draft процессора.

`/reset_state <platform> <platform_user_id>`

Безопасно сбрасывает только состояние заполнения формы пользователя. Тикеты и данные в БД не закрывает и не удаляет. Используйте, если пользовательская форма зависла на старой кнопке или неконсистентном шаге.

`/close`

Запасная команда закрытия. Не закрывает тикет сразу, а показывает inline-кнопки с причинами закрытия. Если у формы есть `close_reasons`, бот показывает причины этой формы; если формы уже нет в YAML или причины не заданы, используются общие причины:

- `✅ Решено`
- `👤 Нет ответа от пользователя`
- `🔁 Дубликат`
- `⛔ Нарушение правил`
- `📝 Другая причина`

После выбора причины бот закрывает тикет, сохраняет `close_reason`, заполняет `closed_at` и `closed_by_telegram_id`, пишет причину в topic и отправляет её пользователю. Повторный выбор старой причины по уже закрытому тикету не меняет данные и отвечает `Тикет уже закрыт.`

## Закрытие кнопкой

Закрытие нового тикета работает через reply keyboard в topic поддержки. Бот отправляет:

```text
Управление тикетом #42
```

и keyboard-кнопку:

```text
✅ Закрыть тикет
```

Когда администратор нажимает кнопку, бот ищет активный тикет по текущему `message_thread_id`. Если тикет уже закрыт или отменён, бот отвечает `Тикет уже закрыт.` Системные keyboard-команды поддержки не пересылаются пользователю.

Причины закрытия показываются inline-кнопками. После закрытия бот убирает reply keyboard через `ReplyKeyboardRemove`, сохраняет `close_reason`, пишет в topic `Причина: ...` и отправляет пользователю `user_message` выбранной причины или стандартный текст.

## Напоминания

Если `TICKET_REMINDER_ENABLED=true`, бот периодически проверяет открытые тикеты. Интервал проверки задаёт `TICKET_CHECK_INTERVAL_MINUTES`.

Если тикет открыт дольше `TICKET_REMINDER_AFTER_HOURS`, бот отправляет в topic:

```text
⏰ Тикет открыт больше 24 часов.
Пожалуйста, проверьте обращение или закройте тикет, если вопрос решён.
```

Чтобы не спамить, повторное напоминание по тому же тикету отправляется не чаще, чем раз в `TICKET_REMINDER_INTERVAL_MINUTES`. Для этого бот хранит `last_reminded_at`.

Если напоминания не отправляются, проверьте `.env`, что scheduler включён, бот запущен после миграций, а у бота есть право писать в topic. Подробная ошибка будет в логах.

## Ожидание ответа пользователя

Если `USER_REPLY_REMINDER_ENABLED=true`, бот проверяет тикеты со статусом `waiting_user`. Через `USER_REPLY_REMINDER_AFTER_HOURS` часов после последнего ответа поддержки пользователь получает сообщение на исходную платформу:

```text
⏳ Поддержка ожидает ваш ответ.

Пожалуйста, напишите сообщение сюда.
```

Повторное напоминание ограничено `USER_REPLY_REMINDER_INTERVAL_HOURS`. Если значение `0`, бот отправляет только одно напоминание. Заблокированным пользователям напоминания не отправляются; если доставка не удалась, ошибка пишется в лог и в topic тикета.

## Автозакрытие

Если `TICKET_AUTO_CLOSE_ENABLED=true`, бот закрывает активные тикеты (`open`, `in_progress`, `waiting_user`), где пользователь не писал дольше `TICKET_AUTO_CLOSE_AFTER_DAYS` дней. Считается именно последнее сообщение пользователя, поле `last_user_message_at`; ответы администрации его не обновляют.

Если `TICKET_AUTO_CLOSE_WARNING_ENABLED=true`, за `TICKET_AUTO_CLOSE_WARNING_HOURS` часов до автозакрытия бот один раз предупреждает пользователя:

```text
⏰ Ваш тикет будет закрыт через 24 часа, если вы не ответите.
```

Поле `auto_close_warning_sent_at` не даёт повторять предупреждение по тому же периоду неактивности. Если пользователь ответил после предупреждения, поле сбрасывается и при новой длительной неактивности предупреждение может отправиться снова.

При автозакрытии сохраняется `close_reason=auto_no_user_response`, `closed_by_telegram_id` остаётся пустым, бот пишет в topic причину и отправляет пользователю уведомление с меню форм на его платформе. Если уведомление пользователю не удалось отправить, тикет всё равно закрывается, ошибка пишется в лог и topic.

## Клавиатуры пользователя

Reply-клавиатура с формами появляется после `/start`, после отмены заполнения тикета, после закрытия администрацией и после автозакрытия. При открытом тикете или во время заполнения бот убирает пользовательскую клавиатуру форм, чтобы пользовательские кнопки не попадали в группу поддержки.

## Редактирование сообщений

Бот хранит связи копий сообщений в `message_maps`.

Если пользователь редактирует сообщение, бот пытается отредактировать уже отправленную копию в topic поддержки. Для текста используется `edit_message_text`, для caption медиа — `edit_message_caption`.

Если поддержка редактирует сообщение в topic, бот пытается отредактировать уже отправленную копию у пользователя.

Если Telegram не разрешает редактирование, тип сообщения изменился, сообщение слишком старое или связь не найдена, бот пишет fallback-уведомление и логирует ошибку.

## Частые проблемы

Если бот не создаёт topic, проверьте, что группа является форумом, бот добавлен администратором и имеет право создавать топики.

Если ответы поддержки не доходят пользователю, проверьте, что BotFather privacy mode отключён, бот находится именно в `SUPPORT_CHAT_ID`, а сотрудник пишет внутри связанного topic.

Если не работает редактирование сообщений, проверьте логи. Telegram разрешает боту редактировать только сообщения, которые отправил сам бот, и не позволяет превращать текст в медиа или один тип медиа в другой.
